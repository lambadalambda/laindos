# Verify Sam & Max root installer selection launch

## Summary

The Sam & Max CD root installer reaches its text menu under QEMU `-icount shift=6`, and a fresh selection probe now shows the menu actually performs `CHDIR` plus `EXEC` of the configured action. The remaining `Bad command or file name` the user sees after the action flashes is generated by the action's batch file itself, not by `INSTALL.EXE`. Tracking the installer's own `Enter` handling further would be cosmetic.

## Requirements

- Verify that selecting an installer menu entry launches the configured command instead of only changing directory.
- Keep any Sam & Max coverage vendor-gated and out of the default `make test` ladder.
- Do not seed `C:\SAMNMAX.CD\SETMUSE.INI` or add a Sam & Max-specific kernel workaround.

## Acceptance Criteria

- A manual or automated probe can select `SAM & MAX` from the root installer and observe the configured launch path progressing past the installer menu.
- If automated, the probe records stable screen or serial markers and is wired behind an explicit vendor-gated target.
- Relevant debug notes are updated with the verified result.

## Notes

- The likely generic root cause was fixed by making `INT 21h AX=4B00h` env segment `0` inherit the parent PSP environment instead of generating `COMSPEC` from the current drive.
- A focused multidrive regression now covers that behavior by launching `A:\ENVTEST.COM` while the parent current drive is `C:`.
- The original `sendkey` mystery was a probe-side limitation: the installer's text-menu draw places the highlight on the first row by default; `Esc` triggers the explicit abort path while `Enter` reaches the main action loop. QEMU HMP `sendkey ret` does deliver the key, but the resulting `BDA` head/tail advance and screen redraw are too fast for serial-only markers, so we read attribute bytes (offset 0xB8000 attributes) to confirm that the highlight does move and that the installer's screen returns to the same state after the action.
- The actual user-visible failure was downstream of the installer: the per-row actions in `INSTALL.CFG` point at `start.bat` files such as `D:\REBEL\START.BAT` whose contents call MS-DOS shell utilities. For example `D:\REBEL\README.BAT` runs `more < font\readme.txt` and `D:\REBEL\START.BAT` calls `pause >nul` then chains to `rebel.bat`. LainDOS now covers the `PAUSE`, `MORE`, `BREAK`, `MODE CO80`, `> nul`, and `< file` subset used by these batches; `@` prefixes and batch parameter expansion remain separate shell-compatibility work.
- Sam & Max's `SAM.EXE` and `DOS4GW.EXE` themselves are still protected-mode Windows 3.1 binaries, so even if the installer executed them cleanly, LainDOS's real-mode-only kernel would not run them. The action-launching path is working as far as LainDOS is concerned; the demos fail because they need a full MS-DOS environment.
- A focused probe (`scripts/test_sammax_cd_install_select.py`) drives the menu with attribute-aware screen capture, confirming that `sendkey ret` is consumed and the menu is redrawn. The probe is intentionally not a default test because it depends on the vendor archive.

## Follow-up Investigation If Ever Needed

- If the user wants a fully working demo chain, remaining shell-compatibility work includes `@` prefix handling, batch argument expansion for `%1`..`%9`, and any extra utilities reached by deeper demo-specific chains. The main protected-mode/Win16 binaries remain out of scope for real-mode LainDOS.
- If the user wants the auto-runner (`scripts/test_sammax_cd_install.py` smoke) to drive the menu end-to-end without manual VNC, the QEMU monitor's VNC/RFB input injection would be more reliable than `sendkey`, since attribute dump shows the highlight does move but the auto-launch produces a too-fast action flash.
